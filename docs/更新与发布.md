# 更新与发布

GitHub 保存源码和安装包，GitHub Actions 自动完成检查、测试、打包与正式发布。应用数据继续保存在用户电脑中。

## 使用者：安装新版本

1. 在软件「设置 → 检查更新」中查看是否有新版本，点击「前往下载新版本」；也可以直接打开 [Releases](https://github.com/qzm-qzm/super-brain/releases/latest)。
2. 更新前可以用「导出备份」保存一份副本。
3. 从托盘菜单或设置中彻底退出超强大脑；关闭小窗只是收起。
4. 安装版下载新的 `SuperBrain-Setup-版本号-x64.exe`，按原安装方式覆盖安装即可。免安装版改用新的 `SuperBrain-Portable-版本号-x64.exe`。
5. 再次启动，备忘录、密码库和外观仍从 `%APPDATA%/SuperBrain` 读取。

当前采用手动检查、下载和安装更新，不会在后台静默替换程序。不要手动删除用户数据目录。免安装版也使用这个目录，替换 EXE 不会替换资料。

如果新版本涉及数据格式迁移，发布说明应单独解释兼容性。当前版本不提供自动降级迁移；需要回退时，使用相应旧版本与升级前的备份。

## 维护者：修改功能

先在 Windows 上安装 Node.js 24 与 Git，克隆仓库，然后安装依赖：

```powershell
git clone https://github.com/qzm-qzm/super-brain.git
cd super-brain
npm ci
node node_modules/electron/install.js
```

每次修改后执行：

```powershell
npm run check
npm test
npm run test:desktop
npm start
```

`npm run test:desktop` 使用 Playwright 启动真实 Electron，在 `test-results/desktop-smoke-*` 中创建独立资料和虚构记录，检查界面、IPC、文件保存、锁定以及重启恢复。它不会使用日常资料，不需要额外安装 Playwright 浏览器。运行结束可在对应目录查看 `result.json` 和截图。

还需手动确认全局快捷键、托盘、开机启动和备份对话框等系统交互。开发运行 `npm start` 默认使用真实用户数据目录；请按[使用说明](使用说明.md#开发时隔离测试资料)配置独立测试资料。

更新 `CHANGELOG.md`，将通过验证的功能改动提交或合并到 `main`。推送后可以在 [Actions](https://github.com/qzm-qzm/super-brain/actions) 查看自动检查和 Windows 构建。

## 维护者：发布新版本

在 `main` 上完成修改并提交，使工作区保持干净。先确认 `git status`，再选择一种升级方式：

```powershell
# 修复问题，例如 0.1.0 → 0.1.1
npm version patch -m "chore: release v%s"

# 推送 main 和刚创建的带注释版本标签
git push origin main --follow-tags
```

添加一批新功能时，使用 `npm version minor -m "chore: release v%s"`，例如从 `0.1.1` 升为 `0.2.0`。需要不兼容的大版本更新时再考虑 `major`。

`npm version` 会同步更新 `package.json` 与 `package-lock.json`，创建版本提交和 `v版本号` 标签。不要在同一次发布中连续运行多个 `npm version` 命令。仓库应使用默认的 `v` 标签前缀，工作流只接受 `v数字.数字.数字`，并要求与两个 package 文件中的版本完全一致。

首次发布已有的 `0.1.0` 时，不需要再升号；确认对应提交位于 `main` 后，使用：

```powershell
git tag -a v0.1.0 -m "Release v0.1.0"
git push origin main --follow-tags
```

发布不需要额外填写个人访问令牌；工作流使用 GitHub 提供的短期 `GITHUB_TOKEN`，仅发布任务申请 `contents: write`。仓库的 Actions 功能必须启用，并允许运行官方 `actions/*`。

## 自动工作流做什么

| 触发方式 | 执行内容 |
| --- | --- |
| 推送 `main` | `npm ci`、安装 Electron runtime、语法检查、单元测试、`npm run test:desktop`，然后构建 Windows x64 安装包及免安装包 |
| 向 `main` 提交 PR | 安装依赖、安装 Electron runtime、语法检查、单元测试和桌面集成测试；不发布 |
| 推送 `v*` 标签 | 校验版本号、完成检查和构建、生成 SHA-256 校验文件、发布 GitHub Release |
| Actions 手动运行 | 对选择的分支或标签检查并构建，生成可下载 artifact；不创建正式 Release |

构建任务只有仓库读取权限。发布任务独立运行，只接收前一步的安装包与校验文件，不运行项目依赖安装脚本。先创建草稿并上传所有附件，再公开 Release；上传中途失败时，草稿不会成为用户可下载的最新正式版本。

每次非 PR 构建都会在运行详情页的 **Artifacts** 下保存 `SuperBrain-版本号-windows-x64`，保留 14 天，需要登录 GitHub 下载。正式用户下载应使用 Release 附件；这些文件不会因 Actions artifact 的 14 天保留期而自动删除。

桌面集成测试失败时，工作流会尝试保留 `SuperBrain-desktop-failure-*` 诊断产物 7 天，只包含独立测试目录的结果摘要与截图，内容均为测试生成的虚构样本。构建与发布是否成功以 Actions 对应运行的实际状态为准。

正式版本包含：

- `SuperBrain-Setup-版本号-x64.exe`：安装版。
- `SuperBrain-Portable-版本号-x64.exe`：免安装版。
- `SHA256SUMS.txt`：上述两个文件的 SHA-256。

发布说明会包含下载和数据保留提示，以及 GitHub 自动生成的改动列表。需要更具体的用户说明时，可在 Release 页面编辑正文。不要重新打包覆盖已经发布的同一个版本；修改后发布新版本。

## 发布失败时

先打开失败的 Actions 运行，查看具体步骤。版本不一致时，用新的正确版本提交和标签重新发布；网络下载或上传暂时失败时，可以在该运行中使用 **Re-run failed jobs**。同一版本如果只留下草稿，重试会补齐附件再发布；如果已经是公开 Release，工作流会停止，避免悄悄替换用户下载过的文件。

如果只是手动运行工作流，生成 artifact 而没有正式 Release 是预期行为。正式发布需要推送一个尚未发布、版本匹配的 `v*` 标签。

## 检查下载完整性

把安装包和 `SHA256SUMS.txt` 下载到同一个目录，使用 PowerShell 计算文件摘要：

```powershell
Get-FileHash -LiteralPath .\SuperBrain-Setup-0.1.0-x64.exe -Algorithm SHA256
Get-Content -LiteralPath .\SHA256SUMS.txt
```

将输出与同一文件名对应的摘要比较，大小写不影响比较。校验值用于检查完整性，不能消除当前安装包未签名这一限制。
